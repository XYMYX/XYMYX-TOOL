# sha256

Files: `src/core/sha256.h`, `src/core/sha256.cpp`

SHA-256 is implemented from scratch here. It is about 100 lines, needs no library, and is a good algorithm to read once in your life.

## What a hash is

A hash function takes any amount of data and produces a fixed-size fingerprint. For SHA-256 that is 256 bits, written as 64 hexadecimal characters.

Three properties make it useful:

- **Deterministic.** The same input always gives the same hash.
- **Avalanche.** Changing a single bit of the input changes about half of the output bits.
- **One-way.** You cannot work backwards from the hash to the input, and nobody has found two different inputs with the same SHA-256.

That is why download pages publish hashes: if the hash of your file matches, the file is bit for bit what the author uploaded.

## The algorithm, step by step

The class `Sha256` keeps a **state** of eight 32-bit numbers. Data is processed in **blocks** of 64 bytes. Each block stirs the state.

### 1. Start values

The constructor sets the state to eight fixed numbers. They are the first 32 bits of the fractional parts of the square roots of the first eight primes. The 64 round constants in `kRound` come from cube roots of primes in the same way.

Why such odd numbers? Because nobody could have picked them to hide a weakness. Cryptographers call these "nothing up my sleeve" numbers.

### 2. Cutting data into blocks: `update`

`update` can be called many times with pieces of any size. It handles three cases:

- A partial block is waiting in `buffer_`: fill it up first.
- Full 64-byte blocks: process them directly from the caller's memory.
- A leftover smaller than 64 bytes: keep it in `buffer_` for next time.

This is what allows `sha256File` to hash a file of any size while holding only 1 MB in memory.

### 3. Mixing one block: `transform`

**Message schedule.** The 64 bytes are read as 16 words of 32 bits, most significant byte first. Those 16 words are then expanded to 64 words. Each new word is built from four earlier ones using rotations, shifts and XOR. This spreads every input bit across many rounds.

**64 rounds.** The state is copied into eight working variables `a` to `h`. Each round:

- combines them with two small functions,
  - "choose": each bit of `e` picks the matching bit from `f` or `g`,
  - "majority": each bit is what at least two of `a`, `b`, `c` have,
- adds one round constant and one schedule word,
- shifts all eight variables along by one position.

**Add back.** After 64 rounds the working variables are added to the old state. All additions wrap around at 32 bits; that is simply what `std::uint32_t` does in C++.

`rotr` is a rotate: bits that fall off the right end re-enter on the left. Unlike a shift it loses nothing.

### 4. Padding and output: `hex`

A message rarely ends exactly on a block boundary, so the standard defines padding:

1. Append one byte `0x80` (a single 1 bit).
2. Append zero bytes until 8 bytes are left in the block.
3. Append the message length in bits as a 64-bit number.

If fewer than 9 bytes are free in the last block, the padding continues into one extra block. That is the `56` / `120` calculation in `hex`.

Putting the length into the padding matters: without it, a message and the same message with extra zero bytes could collide.

Finally the eight state words are written as hexadecimal, four bits per character.

## Hashing a file: `sha256File`

Two details are worth noticing:

- The file is opened in **binary mode**. In text mode Windows would convert line endings while reading, and the hash would be of different bytes than those on disk.
- After the read loop it checks `in.bad()`. Reaching the end of the file is normal. A read error is not, and returning the hash of half a file would be worse than returning nothing. The function then returns an empty `std::optional`.

## How it was checked

The implementation was compared against Windows' own `Get-FileHash` on a set of files chosen to hit the tricky spots: an empty file, the classic test string `abc`, files of 55, 56 and 64 bytes (the padding boundaries) and a 3 MB file (many blocks, a partial last read). All matched.

You can check it yourself:

| System | Command |
| --- | --- |
| Windows PowerShell | `Get-FileHash file.bin -Algorithm SHA256` |
| macOS | `shasum -a 256 file.bin` |
| Linux, WSL | `sha256sum file.bin` |

Known answer: the SHA-256 of the three bytes `abc` starts with `ba7816bf`.

## Should you write your own crypto?

For learning, yes. For a product, normally not: use a well-reviewed library. A hash function is the mild case, because it has no secret key and is easy to verify against test vectors. Anything involving keys, such as encryption or signatures, is far easier to get subtly wrong.
